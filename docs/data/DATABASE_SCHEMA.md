# Relational Database Schema

## Conventions

- PostgreSQL is the system of record.
- Tables and columns use `snake_case`.
- Domain entities use UUID primary keys generated by the backend.
- Imported employee IDs and human labels are alternate keys, not primary keys.
- Timestamps are UTC `timestamptz`.
- Floor coordinates are integer world units; Template Revision vertices are integer template-local coordinates using the same 10-centimetre unit.
- Lifecycle records use archive/status columns instead of destructive deletion.
- Domain data is normalized; JSON and JSONB columns are prohibited.
- Every mutable table carries `created_at`, `updated_at`, and, where useful, actor identifiers.

The schema below is logical. Migration files remain the executable authority once implementation begins.

## Identity and authorization

### `organizations`

| Column | Constraints |
|---|---|
| `id` | UUID primary key |
| `name` | text, unique, required; initially `Arrise` |
| `archived_at` | nullable timestamp |

There is one Organization in the MVP. The table makes ownership explicit without turning organization ID into a repeated tenant-isolation key.

### `app_users`

| Column | Constraints |
|---|---|
| `id` | UUID primary key |
| `organization_id` | FK `organizations`, required |
| `email` | case-insensitive text, unique, required |
| `display_name` | text, required |
| `active` | boolean, required |
| `last_login_at` | nullable timestamp |

### `app_user_identities`

| Column | Constraints |
|---|---|
| `id` | UUID primary key |
| `app_user_id` | FK `app_users`, required |
| `provider` | `LOCAL` or `ENTRA`, required |
| `provider_subject` | text, required |
| `created_at` | timestamp, required |

Unique `(provider, provider_subject)` and `(app_user_id, provider)`. For Entra, `provider_subject` is the immutable object ID. Email is never used as an external identity key.

### `local_auth_credentials`

Development-only credentials: `app_user_id` as PK/FK, unique case-insensitive `username`, Argon2id `password_hash`, `password_changed_at`, and optional `disabled_at`. No plaintext password is stored.

### `local_auth_sessions`

Development-only opaque sessions: UUID ID, `app_user_id`, unique `token_hash`, `created_at`, `expires_at`, nullable `revoked_at`, and optional safe client metadata. Expired and revoked sessions are rejected and may be pruned.

### `roles`

Seeded rows use stable codes: `SYSTEM_ADMIN`, `FACILITIES_ADMIN`, `WORKPLACE_PLANNER`, and `VIEWER`. `SYSTEM_ADMIN` is an operational access-administration role and grants no domain-data access by itself.

| Column | Constraints |
|---|---|
| `id` | small integer primary key |
| `code` | text, unique, required |
| `name` | text, required |

### `app_user_roles`

| Column | Constraints |
|---|---|
| `app_user_id` | FK `app_users` |
| `role_id` | FK `roles` |
| `granted_by_user_id` | FK `app_users`, required |
| `granted_at` | timestamp, required |
| `revoked_at` | nullable timestamp |

The primary key includes user, role, and grant time. A partial unique index permits at most one unrevoked grant for each user-role pair.

## Location hierarchy

### `sites`

`id`, `organization_id`, unique `code`, `name`, optional address fields, time zone, and `archived_at`.

### `buildings`

`id`, `site_id`, unique `(site_id, code)`, `name`, and `archived_at`.

### `floors`

`id`, `building_id`, unique `(building_id, code)`, `name`, optional ordinal, and `archived_at`.

### `floor_plans`

| Column | Constraints |
|---|---|
| `id` | UUID primary key |
| `floor_id` | FK `floors`, unique, required |
| `name` | text, required |
| `archived_at` | nullable timestamp |

One stable Floor Plan identity belongs to each Floor.

### `floor_plan_revisions`

| Column | Constraints |
|---|---|
| `id` | UUID primary key |
| `floor_plan_id` | FK `floor_plans`, required |
| `revision_number` | positive integer, required |
| `status` | `DRAFT`, `PUBLISHED`, or `ARCHIVED` |
| `based_on_revision_id` | nullable self-FK |
| `editing_scale` | integer in `1,2,4,8,16,32,64,128,256` |
| `concurrency_version` | non-negative bigint |
| `created_by_user_id` | FK `app_users`, required |
| `published_by_user_id` | nullable FK `app_users` |
| `published_at` | nullable timestamp |

Constraints and indexes:

- unique `(floor_plan_id, revision_number)`;
- at most one Draft per Floor Plan;
- at most one Published revision per Floor Plan;
- publication metadata is present exactly when status is Published or Archived after publication;
- published and archived revisions are read-only.

### `floor_plan_editor_leases`

| `app_user_id` | FK `app_users`, required |
| `lease_token_hash` | text, required |
| `acquired_at` | timestamp, required |
| `expires_at` | timestamp, required |
| `renewed_at` | timestamp, required |

Only Draft revisions may have leases.

## Polygon vertex storage

Each polygon-owning entity has a dedicated vertex table. This repeats a small table shape but preserves strict foreign keys and prevents a polygon from being orphaned or shared accidentally. In the MVP, direct polygon owners are Floor Boundaries and Element Template Revisions; all other floor geometry is a transformed placement of a template.

Every vertex table contains:

| Column | Constraints |
|---|---|
| owning entity ID | FK to its parent |
| `sequence` | integer beginning at 0 |
| `x` | integer, required |
| `y` | integer, required |

The primary key is `(owning entity ID, sequence)`. A unique constraint on `(owning entity ID, x, y)` prevents repeated vertices. Sequence values must be contiguous. The backend validates closure, anticlockwise orientation, orthogonality, and topology.

Owning records may cache vertex count, bounds, and signed double area transactionally for validation and read performance. Vertices remain authoritative.

## Template catalog

### `element_categories`

`id`, `organization_id`, unique `(organization_id, code)`, `name`, optional `parent_category_id`, display order, and `archived_at`.

### `element_templates`

`id`, `element_category_id`, stable unique code within the category, name, description, `current_revision_id`, and `archived_at`.

The `current_revision_id` FK is nullable during initial creation and must reference a revision belonging to the same template.

### `element_template_revisions`

| Column | Constraints |
|---|---|
| `id` | UUID primary key |
| `element_template_id` | FK `element_templates`, required |
| `revision_number` | positive integer |
| `assignable` | boolean, required |
| `spatial_class` | `PHYSICAL`, `ZONE`, or `OBSTACLE` |
| `border_color` | validated RGB hex text |
| `fill_color` | validated RGB hex text |
| `created_by_user_id` | FK `app_users`, required |
| `created_at` | timestamp, required |

Unique `(element_template_id, revision_number)`. Revisions are immutable after creation. An assignable revision must use the `PHYSICAL` spatial class.

### `element_template_revision_vertices`

Ordered local integer coordinates keyed by `(element_template_revision_id, sequence)`.

## Revision geometry

### `floor_boundaries`

| Column | Constraints |
|---|---|
| `floor_plan_revision_id` | PK and FK `floor_plan_revisions` |

### `floor_boundary_vertices`

Ordered world coordinates keyed by `(floor_plan_revision_id, sequence)`.

### `placement_identities`

| Column | Constraints |
|---|---|
| `id` | UUID primary key |
| `floor_plan_id` | FK `floor_plans`, required |
| `created_at` | timestamp, required |

This identity persists while a logical physical element, Zone, or Obstacle is copied through Floor Plan Revisions.

### `placed_elements`

| Column | Constraints |
|---|---|
| `id` | UUID primary key |
| `floor_plan_revision_id` | FK `floor_plan_revisions`, required |
| `placement_identity_id` | FK `placement_identities`, required |
| `element_template_revision_id` | FK `element_template_revisions`, required |
| `position_x`, `position_y` | integers, required |
| `rotation_degrees` | integer in `0,90,180,270` |
| `label` | nullable text |

Constraints and indexes:

- unique `(floor_plan_revision_id, placement_identity_id)`;
- unique label within a Floor Plan Revision when label is present;
- placement identity must belong to the same Floor Plan;
- no placement-level dimensions or scale columns.

The referenced Template Revision’s `spatial_class` determines whether the placement behaves as a physical element, Zone, or Obstacle. Creating a custom Zone or Obstacle therefore creates an immutable Template Revision first and then places it; the three spatial classes do not use parallel floor-specific polygon tables.

`id`, unique `code`, `name`, and `active`.

### `teams`

`id`, optional `department_id`, unique `code`, `name`, and `active`.

### `employees`

|---|---|

## Allocation

### `assignments`

| Column | Constraints |
|---|---|
| `id` | UUID primary key |
| `employee_id` | FK `employees`, required |
| `placement_identity_id` | FK `placement_identities`, required |
| `starts_at` | timestamp, required |
| `ends_at` | nullable timestamp, later than `starts_at` |
| `created_by_user_id` | FK `app_users`, required |
| `ended_by_user_id` | nullable FK `app_users` |
| `created_at` | timestamp, required |

Rules:

- periods for one `placement_identity_id` may not overlap;
- overlapping periods for one Employee across different spaces are allowed;
- the target identity must resolve to an assignable placement in the applicable Published revision;
- historical rows are never deleted when an Employee or placement is archived.

A PostgreSQL exclusion constraint over placement identity and a timestamp range is preferred for final protection, with equivalent domain validation for clear error messages.

## Reliability and audit

### `processed_commands`

Stores client command ID, user, route or command type, request hash, result reference, and expiration. It supports idempotent retry without storing domain payloads as JSON.

### `audit_events`

Stores immutable event ID, timestamp, actor user ID, action code, target type, target textual ID, correlation ID, and a safe summary. Audit rows contain no access tokens, spreadsheet rows, or unrestricted before/after snapshots.

## Indexing baseline

- All foreign keys receive supporting indexes.
- Active and status-filtered screens use partial indexes where appropriate.
- Employee search indexes normalized employee ID, name, and email.
- Placement lookup indexes revision ID, template revision ID, and label.
- Assignment lookup indexes employee, placement identity, and start/end time.
- Vertex access uses each parent-and-sequence primary key ordering.

Indexes are verified against measured queries rather than added speculatively beyond this baseline.

## Deletion and retention

- Published or historically referenced records are archived.
- Hard deletion is restricted to unreferenced drafts, staging rows past retention, and failed imports past retention.
- Import source files are temporary and deleted after validation or a short operational retention period.
- Audit and assignment retention follows Arrise policy, which must be confirmed before production.
